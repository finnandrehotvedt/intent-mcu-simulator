# Compatibility

Intent MCU Simulator 1.1.0-rc.126 publicly executes one `ATmega328P`, 16 MHz,
5 V learning profile, one bounded `RP2040 Pico` GPIO0/UART0 source profile and
one bounded `ESP32-C3` GPIO2/UART source profile, plus one bounded
`STM32F429ZI` PB0/USART3/reset-replay profile. They are educational subsets,
not complete electrical or cycle-perfect hardware replacements.

X46 currently supports only read-only AVR USART0 TX byte events retained by
the current identity-bound paused worker. It validates complete ordered
records, exact avr8js integer-baud quantization and exact model frame cycles,
then shows byte values, text and cycle deltas. It does not infer UART framing,
RX data, physical voltage/noise, I2C or SPI and grants no Apply, Build, Run or
verdict authority. X46 remains partial.

X48 adds one bounded discrete ideal-room loop for the exact AVR thermostat
starter. It requires one fresh paused cycle-zero worker and exact source,
graph, artifact and model joins. Its 32 instruction-boundary observations are
independently recomputed and require HIGH/LOW phase coverage with zero drops.
It is not physical thermal calibration, wall-clock timing, a continuous solver,
general process-model support or safety evidence.

The X81 disclosure is a local, read-only assessment of one reviewed retained
AVR fixture. It recomputes the release-owned envelope for two recorded workers
and the first 512 paused instructions. Matching ideal CPU/GPIO/UART observations
do not establish independent rebuild-byte equality or physical equivalence.
Import and reopen add no Build, Run, project, runtime or verdict authority.
X81 is complete against this bounded assessment criterion after independent
public reopen of the actual saved envelope reproduced the verified observation
result and explicit `not-checked` rebuild-byte axis. An ordinary firmware Run
is outside this local data-only criterion; physical and rebuild-byte claims
remain absent.

X57 accepts only strict inert contribution manifests against current hashed
bytes. A trusted maintainer must explicitly review every declared change class,
and only three fixed project-owned conformance owners may run. Admission adds
no registry entry and grants no execution, runtime, release or network
authority. X89 assesses exact local configuration and pinned image identities
without starting Docker; service health, compiler readiness, firmware execution
and physical readiness remain separate and untested.

The X69 recipient walkthrough accepts only canonical strict-v3 AVR thermostat
experiment packages. It displays authored schedules and retained observations
as historical evidence, never as a fresh execution or current verdict. X74
uses explicit local downloads and opens for one strict data-only response bound
to exact parent bytes. Neither feature adds accounts, uploads, server project
storage, automatic Apply, sender authentication, execution or runtime state.

The optional current-tab experiment budget has reviewed native owner-quiescence
evidence for its bounded AVR, RP2040 Pico, ESP32-C3 and STM32 slices: trusted session
start, fixed aggregate limits, atomic dispatch ownership, inert review files,
Pico Pause acknowledgements and exact C3 process-retirement proof. ESP32-C3
CPU/UART is actual QEMU execution while GPIO2 remains a separately labelled
project-owned model. STM32 binds request, source, graph, ELF, model, compiler
and runtime identities to authenticated natural completion and exact daemon-
container absence. Its accepted Renode proof observes final PB0 and USART3
across reset replay using instruction ordinals, not physical cycles or timing;
the external LED remains an ideal teaching rendering. Existing manual controls on all four
profiles are unchanged; this does not provide a generic AI agent, remote
scheduler, billing quota or cross-user budget. X92 remains partial.

Canvas annotations are local, non-electrical presentation data. Notes and
groups cannot create components, pins, subcircuits or connectivity. Net labels
bind only an existing canonical net ID, display that ID, and cannot create,
merge, split or retarget a net even when label text matches. The annotated
wrapper is strict and versioned; invalid or dangling references fail closed
without replacing the last accepted project. The finite AVR subcircuit owner
admits only one non-nested resistor-and-LED series definition with explicit
source and ground port bindings and deterministic expansion into the ordinary
validated graph. It is not general-purpose or other-profile subcircuit support.
The default thermostat candidate uses the exact locked candidate validator;
unknown component types still fail closed and the runtime receives only the
fully validated expanded ordinary graph.

The presentation view is AVR-only and read-only. Each start captures one
labelled observation snapshot; moving between steps never refreshes from live
instrument DOM. A new start is required for newer values. Presentation data
cannot Build, Run, Apply or grant verdict authority.

The teaching exercise package is limited to one local AVR exercise with the
correct and known-bad equality variants. Contained projects remain strict
learner-owned data and require an explicit trusted-human Open action. No remote
catalogue, account, automatic execution or other-profile exercise is implied.

The X92 fixed-default exhaustion browser proof is parser- and UI-bound but its
accepted downstream actions are synthetic. It adds no native producer,
profile equivalence or full X92 closure.

All four profiles expose the same two finite original body presets for their
existing fixed resistor. The selection is layout-only authored data. It cannot
change pins, nets, resistance, source, model or runtime state and does not
constitute a general component, model or drawing editor.

All four profiles also expose two finite original outline presets for their
existing shared LED. Outline is layout-only and independent from the LED's
electrical colour and ideal forward-voltage model. It cannot move
ANODE/CATHODE anchors, alter nets, load arbitrary geometry or create a model.

The existing resistor and LED additionally expose bounded body width, height
and corner-softness controls. Width and height stay within 80–100% of the
project-owned envelope and corner softness within 0–100%. Rendered lead
contacts follow accepted body edges, but electrical anchors, world bounds,
nets, routes and model behavior remain fixed. This is not arbitrary geometry
or a general component, model or drawing editor.

The existing resistor and LED Inspector now separates electrical model values
from finite Drawing controls. Model Preview is non-mutating; accepted model
Apply retains the existing bounded property contract and circuit validation,
clears stale executable/runtime evidence and requires a fresh Build before Run.
Drawing Apply remains layout-only. This separation adds no property, pin, net,
geometry range, arbitrary drawing or new runtime behavior.

Pico, ESP32-C3 and STM32 expose bounded orthogonal cable layout editing with
six fixed colours. These controls modify only accepted local layout data.
Named endpoints and the existing net graph remain the sole electrical
authority; crossings do not connect nets, and distinct nets cannot share a
positive-length collinear lane.

Fault validation is bounded to each representable profile. AVR detects its
named 5 V-to-ground short, known opposing logical outputs and declared 5 V
supply-role mismatch. All profiles reject their representable missing-ground,
LED-polarity, required-resistance and ideal-model overcurrent faults with a
corrective action. This is not arbitrary rail mixing, a general circuit solver,
physical damage prediction or safety certification.

AVR projects allow every selectable catalogue part to be click-placed or
drag-placed, moved, rotated, deleted and duplicated. A duplicate receives a
fresh stable ID, copies authored properties and controls, and starts with no
net references. Existing IDs, nets, endpoints, junctions and routes are
preserved exactly. The narrow profiles retain fixed three-part graphs and do
not claim general placement or duplication.

AVR ordinary and candidate-v3 graphs support explicit junction branches.
Selecting one branch reconnects or deletes only that endpoint; deleting the
whole net remains a separate labelled action. Every accepted operation has one
complete-document Undo/Redo transaction, while rejected operations add no
history. Automatic-route endpoint buttons provide a visible keyboard- and
pointer-operable way to select an exact branch.

All four actual circuit editors use the same dark workbench canvas and grid.
This presentation parity does not alter any profile's component graphics,
named pins, topology, compiler or runtime capability.

The workbench provides multiple deterministic examples for each currently
supported U03 teaching function. AVR has multiple button, ADC, PWM and Serial
examples. Each bounded Pico, ESP32-C3 and STM32 profile has two UART/LED
examples using only its existing fixed source grammar and three-part circuit.
Button, ADC and PWM remain unavailable on those narrow profiles; examples do
not imply a new peripheral, API, pin or topology.

The component contract contains 19 unique public models across these four
profiles. AVR makes 16 available (13 Simulated and 3 Partial); each narrow
profile makes exactly 3 available (its fixed Partial controller, Simulated
resistor and Simulated LED). The remaining profile/model combinations are
explicitly unavailable. Ordinary AVR project-v2 exposes 5 models, while
candidate-v3 exposes 13 by default or all 16 with the All statuses filter.
`src/component-support-matrix.mjs` is the executable derived inventory and the
same matrix is published on `/components.html`.

Every one of the 25 available component/profile cells has at least one public
starter binding. Eight rc.26 AVR references cover the explicit ground symbol,
SPST, SPDT, analogue light, digital light threshold, active buzzer,
seven-segment display and quadrature encoder. They reuse only the existing
candidate-v3 projections, compiler and worker. SPDT and buzzer remain Partial;
the buzzer is a silent logical indicator rather than an acoustic model.

## Supported and tested

- digital GPIO D0–D13, including input, output and pull-up modes;
- external interrupt INT0/INT1 and the implemented pin-change masks;
- single ADC conversions on A0–A5 against the 0–5 V scalar source;
- PWM output on D3, D5, D6, D9, D10 and D11;
- UART 8N1 at the documented 9,600–115,200 baud fixtures;
- `millis`, `micros`, `delay`, `delayMicroseconds`, deterministic reset and
  bounded instruction stepping;
- project models for a controller, fixed resistor, LED, 0 V reference,
  momentary button, potentiometer, SPST toggle, SPDT changeover, quadrature
  encoder, analogue light and temperature sensors, digital light threshold,
  common-cathode RGB LED, active buzzer, common-cathode seven-segment display,
  and 16×2 write-only 4-bit GPIO character LCD.

The source editor accepts `main.ino` plus bounded project-local `.h`, `.hpp`,
`.c` and `.cpp` files. The fixed compile profile is Arduino AVR Boards 1.8.8,
Arduino CLI 1.5.1 and AVR GCC 7.3.0-atmel3.6.1-arduino7. No arbitrary library
installation is supported.

The X42 observer is supported only for AVR's retained authoritative digital
worker transitions. It must be explicitly armed before a future rising or
falling edge and freezes 16 same-channel transitions before the trigger, the
trigger transition and 16 after it. Observation is transient, capped and bound
to exact project, source, artifact, model, runtime and graph lifecycle identity;
dropped or discontinuous rows fail closed. RP2040 has no approved transition
retention bound for this contract, ESP32-C3 exposes project-model GPIO rather
than QEMU pin timing, and STM32 exposes a final observation rather than a
waveform, so X42 is unavailable for those profiles. Open never restores a
capture or runtime authority.

The complete-against-original-criterion X43 Runtime profile is supported only for an already-
current AVR worker. It binds native emulator cycle and executed-instruction
deltas to one exact source, artifact, model and worker lifecycle and derives
exact 16 MHz virtual time. Browser wall throughput is diagnostic only. Dynamic
SRAM heap use, free SRAM, stack contents and live occupancy are unavailable;
RP2040, ESP32-C3 and STM32 profiling are unavailable for this contract. The
accepted current/interval/since-reset stack-pointer observations and observed
address depth satisfy the original bounded precision criterion; no result is a
physical-hardware benchmark.

The complete bounded X47 input sequence is supported only for the exact AVR graph with
one momentary button wired from D2 to one controller ground. It creates one
deterministic active-low pulse preview and applies it only to the same current,
explicitly paused worker whose source, graph, artifact, model implementation,
model execution context, runtime generation and worker epoch match. Stop
requires cancellation before disposal and revokes authority on timeout. Reset,
Build, Open, New, source/graph change and profile change also revoke authority.
Retained receipts are historical non-current evidence only. The exact AVR
thermostat graph additionally supports finite ramp, deterministic seeded-noise
and recorded A1 temperature schedules with declared degrees Celsius and native
cycle units. Apply queues only on the same exact paused worker and never
resumes it. Arbitrary signals, CSV/network import, persistence/replay and all
non-AVR profiles remain unavailable for X47.

The partial X49 temperature-offset comparison is supported only for the exact
AVR thermostat starter and exact unedited source/graph authority. The native
path is fixed to baseline 0 versus candidate +1 °C, uses one explicit
same-origin isolated build and two fresh dedicated workers, and accepts only
complete zero-drop mailbox evidence in the bounded 160 ms virtual window.
Other offsets are calculated previews only. Any source, graph, project,
profile, authoring, artifact, model or worker drift retires the transient
projection. Physical evidence is absent; other sensors, profiles, persistence,
automatic replay and general experiment authoring remain unavailable for X49.

One bounded thermostat experiment uses that same AVR compiler/runtime path.
Its exact graph is an ideal analogue temperature module on A1, an active-low
button on D2 and a D13 → 220 Ω → LED → ground indicator. The 30 °C equality
rule is `measured < setpoint`; three scenarios reset independently and require
executed D13, matching UART and complete input-event evidence in the 160–350 ms
virtual-time window. The serialized candidate compatibility fixture contains
metadata only and cannot authorize execution: current source and projected
circuit are included in the fresh build identity after every Open or edit.

The Pico editor accepts one exact project-owned `main.c` grammar. It can set
GPIO0 HIGH or LOW, emit 1–24 uppercase UART0 characters and halt. The fixed
Arm GNU 14.3.1 toolchain produces a strict source-bound UF2 that runs in the
rp2040js 1.4.0 browser worker. The only validated external topology is GP0
physical pin 1 through one bounded resistor and LED to GND physical pin 3; the
default is a 220 Ω red-LED pair. GPIO25 is
identified separately as an onboard-LED signal and is not a header anchor.

The bounded Pico, ESP32-C3 and STM32 teaching graphs support the same direct
named-pin cable workflow: choose a free source and compatible free target, or
select a cable and reconnect one explicitly chosen endpoint. This is limited
to each controller's existing controller/resistor/LED/ground graph and stable
net IDs. It is not general cross-controller wiring support. Invalid or pending
wire actions block Build and retire stale executable, runtime and LED
authority; Escape cancels a pending choice without changing topology.

Those three graphs also expose one profile-filtered recovery catalogue
containing only the fixed controller, existing resistor and existing LED. A
missing resistor or LED can be restored after data-only Save/Open, but no wire
is inferred. The restored stable part must be connected through the same named
pins before Build. Resistance and LED colour are limited to combinations that
pass the exact 3.3 V / 12 mA ideal-model validator. The colour setting chooses
a tested forward-voltage constant; it is not a physical colour, wavelength or
brightness simulation.

The ESP32-C3 editor accepts one exact Arduino sketch grammar. It can set GPIO2
to `OUTPUT` or `INPUT`, select `HIGH` or `LOW`, and print one bounded uppercase
UART marker. Arduino CLI 1.5.1, Arduino-ESP32 3.3.10, ESP-IDF 5.5.4 and esp-rv32
2601 produce a strict 4 MiB DIO flash image. Actual Espressif QEMU esp32c3
executes the CPU/UART path and reset replay. Executed GPIO MMIO stores feed a
separate IntentForce GPIO2 register/LED model. QEMU pin state is not observed.
The validated GPIO2 J1 pin 4 → bounded resistor → LED → GND J1 pin 6 circuit is editable:
parts and cables can be selected, moved, quarter-turned, deleted and restored
with bounded Undo/Redo. Every circuit edit or local data-only Open retires
executable and LED authority until a fresh successful Build.

The STM32F429ZI editor accepts one exact project-owned C11 grammar. It can set
PB0 HIGH or LOW, emit 1–24 uppercase USART3 characters and halt. The fixed Arm
GNU 14.3.1 toolchain produces a strict source-bound ELF32. Actual Renode 1.17.0
observes PB0 and USART3 across two matching boot epochs. The named external
PB0 → bounded resistor → LED → GND path is an ideal teaching rendering driven by the
observed PB0 level; it is not analogue or physical-board equivalence. Parts and
cables can be selected, moved, quarter-turned, deleted and restored through
bounded Undo/Redo. Every circuit edit or local data-only Open retires ELF and
LED authority until a fresh successful Build.

## Explicitly unsupported

For AVR, SPI, I²C/TWI, EEPROM writes, watchdog activation, analogue comparator use,
ADC free-running/auto-trigger/differential modes, self-programming and physical
board upload stop or remain unavailable. General analogue or mixed-signal
simulation, physical-device access, hosted AI, accounts and cloud project
storage are outside this release. The
Pico profile does not support a general SDK, headers, pointers, arbitrary MMIO,
PIO, DMA, USB, multicore, broad timing or additional peripherals.

The C3 subset does not support arbitrary source, a general SDK, Wi-Fi,
Bluetooth, broad peripherals, exact timing, general ESP32 family compatibility,
QEMU pin readback, or physical-device equivalence. GPIO2 is a real-board
strapping pin and the virtual example is not hardware wiring advice.

The STM32 subset does not support arbitrary C or ELF, an SDK, timer/PWM,
interrupts, broad peripherals, physical timing, general STM32-family
compatibility, device programming or physical-hardware equivalence. Executable
bytes remain transient and are never stored in a saved project.

Visual catalogue entries are not capability claims. A part becomes selectable
only after it has an electrical model, emulator contract and reference tests.
Physical-hardware comparison remains outstanding; do not use the simulator as
electrical-safety or timing certification.
